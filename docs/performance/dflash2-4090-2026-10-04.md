# RTX 4090 DFlash2 final qualification — 2026-10-04

## Decision

Use standalone **Fixed K7** as the default for this tested native-context workload matrix.
For one request with a reused medium prompt (4554 prompt tokens), **Fixed K11** is preferable:
347.2 generated tokens/s versus K7's 329.8. For concurrent generation, K7 is recommended at
C2, C4 and C8 for all three tested context tiers. The maximum measured aggregate rate is
816.7 generated tokens/s at C8 with the reused medium prompt; this is a throughput result,
not a minimum per-request latency claim.

**Auto is functionally valid, but these calibrated profiles do not qualify as faster than the
best standalone fixed policy.** Auto improves single-request throughput over backend None.
Its concurrent geometric-mean result is approximately the None baseline. Selected proposal
compute has no consistent end-to-end advantage over full Auto in this campaign. Keep Auto
Selected opt-in rather than making it the performance default.

The [README](../../README.md#enable-fixed-k7-or-auto-selected) gives production server commands.
[Machine-readable evidence](dflash2-4090-2026-10-04.json) preserves startup identities,
profile cells, paired measurement summaries, resource accounting and recommendation gates.
It deliberately excludes response text and token arrays; the complete local raw reports retain
those exact-output checks.

## Deliverable and repairs

PR [#15](https://github.com/zhongpei/ninfer-4090/pull/15), merged at
`2188cb23859a904b303659965421f141f288fa83`, adds selected-width proposal compute to
calibrated DFlash2. Selected K7/K11 use 8/12 physical proposal columns including the anchor,
while full mode retains 16. K15 remains 16; K0 skips neural proposal. The committed-context
append still consumes all valid features from the preceding round when the route changes.

The follow-up fixes and testing capability included with this report are:

- Repair and register the host proposal-view regression test, and run the real selected-mode
  assertions instead of advertising a separate compact test that did not exercise selected mode.
- Add a native resident session: one immutable model upload per GPU, fresh Engine/Program
  state per job, exclusive ownership and generation-handle-safe teardown.
- Embed the 18-case real-model suite in that session, covering both full and selected modes.
- Add public generation timing sidecars and a single campaign script covering build, CPU
  gates, correctness, calibration and held-out validation. Every comparison uses the same GPU;
  failures stop the campaign and retain evidence.
- Cap KV capacity at `max_context * Engine capacity`. The earlier capacity-one attempt used
  131072 KV tokens with a 32768-token context and was correctly rejected; the runner now uses
  32768 at E1 and 131072 at E8.
- Set `NINFER_AUTO_NATIVE_EXE` for CPU discovery. The two formerly skipped CLI option tests
  passed in a supplementary run; future campaign runs execute them automatically.

This implementation shares immutable model weights, not mutable context or CUDA Graph state.
It retains the public Engine generation route. It does not introduce a Python inference route.

### Measurement scope and ranking

Generation-wave throughput is actual generated tokens divided by the complete wave wall time.
It includes prompt execution and generation, and excludes model/Engine startup and prompt
preparation. This is the primary ranking metric. Public first-token time includes prompt
preparation and submission through the first accepted token. Request decode rate uses the
first-to-last accepted-token interval and `N-1` tokens; it is a different scope from wave rate.

“First” below means an unprimed first wave. Concurrent requests within that wave can reuse a
prefix; it must not be interpreted as every request having an empty cache. “Reuse” means the
later wave with observed natural prefix reuse, not a separately forced cache configuration.

A fixed candidate must be faster in both pairs, have at least 2% median gain over None and
at most 5% paired request-p95 regression. Auto additionally must beat the best fixed arm
under the same qualification gate. Near ties use the simpler qualifying policy. The observed
highest rate and the recommended policy are therefore reported separately. Two orientations
and small request counts make p95 descriptive; these are screening results, not confidence
intervals or a stable tail-latency guarantee. Aggregate geometric means give equal weight to
measured context/concurrency cells, not production traffic frequency.

## Auto profile coverage and effectiveness

The router keys its table by **actual active batch and execution frontier**, not by requested
client concurrency. Frontier upper bounds 1024/8192/32768 cover the corresponding bands.
Selected profiles are schema 2 with `proposal_compute: selected`; the mode is carried by the
profile, not a production `--proposal-compute` flag.

| Profile | Qualified candidate comparisons | Nonzero selected cells | K0 cells out of 24 |
|---|---:|---|---:|
| auto-E1-full | 9/9 | B1/≤1024: K7; B1/≤8192: K15; B1/≤32768: K7 | 21 |
| auto-E1-selected | 9/9 | B1/≤1024: K15; B1/≤8192: K11; B1/≤32768: K7 | 21 |
| auto-E8-full | 5/27 | B2/≤1024: K7; B4/≤1024: K11 | 22 |
| auto-E8-selected | 4/27 | B2/≤1024: K7; B4/≤1024: K15 | 22 |

E1 can execute only B1: its 21 B2–B8 K0 entries are unreachable, not 21 failed single-request
measurements. E8 has only two nonzero cells; all other actual batch/frontier cells retain K0
because no action qualified or the dominant-cell coverage rule was not met. K0 skips neural
proposal while retaining DFlash2 state; it is not backend None. The profiles' training winners
also need not generalize to held-out prompts. This coverage and the measured held-out results
explain why functional Auto support should not be equated with automatic performance superiority.
The report does not attribute a kernel-level cause without profiling evidence.

Auto Full/Selected never qualify as beating the best fixed policy in this held-out matrix.
Auto Selected is approximately 1.99×/2.62× None for single first/reuse, but approximately
1.02×/1.00× for concurrent first/reuse. The appropriate current recommendation is fixed K7,
with the measured medium-reuse K11 exception, rather than further online heuristic changes.

## Separate same-K full/selected evidence

The earlier same-K A/B run is retained under
`profiles/bench/pr15-2026-10-04/ab-prose-c1/comparison.json`. It tests only one C1 prose
workload, Engine capacity eight, context/KV capacity 32768 and two paired orientations.
Its selected/full throughput ratios are K7 **0.942×**, K11 **0.965×**, K0 **0.998×** and
K15 **1.008×**, with equal complete outputs. K0 and K15 are A/A controls. K7/K11 do not
qualify for a compute speedup in that scope. This result is distinct from the resident
held-out campaign, which compares standalone fixed policies and separately calibrated Auto
profiles. Neither result proves that selected compute is intrinsically slower on every workload.
